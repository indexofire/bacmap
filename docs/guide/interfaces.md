# Interfaces: Web, CLI, TUI and JSON API

All four interfaces use the same task engine, gates and audit trail. Use whichever fits the moment;
you can start a task in one and approve it in another.

## 1. Web console

The dashboard leads with the database overview, then tasks, then a **species-first** typing section (choose a species to see its MLST/serotype/AMR/virulence distributions; whole-database mixes are not shown). The default UI is the **Vue 3 console** at `/console/` (Vite build, dark instrument-style
dashboard); `/` redirects there. The old Jinja task console has been removed: legacy paths
(`/tasks`, `/plans`, `/samples`, `/gom`, …) return 307 redirects to their `/console/...`
equivalents. The SPA is served as prebuilt static assets: no Node/Bun is needed at runtime
(ADR-01); Node is only used when rebuilding the frontend.

The console ships **INK / PAPER / CONCRETE themes**: the theme menu in the top bar switches
instantly and persists the choice in `localStorage` (`bacmap-theme`). INK is the dark instrument
console, PAPER is a TailAdmin-like light document surface, and CONCRETE is a Swiss/brutalist
gray template (grid paper, hard rules, Helvetica display, monospaced data, split-screen dashboard
poster). Charts and sample HTML reports follow the theme (`?theme=light|gray`).

**Console login** (single deployment token, no accounts): with `BACMAP_WEB_TOKEN` set and
`BACMAP_WEB_AUTH=cookie`, unauthenticated browser navigation is redirected to `/console/login`
(a Vue login page). After login the top bar shows the operator's token fingerprint and a logout
button. Without a token, auth stays disabled on loopback; in `bearer` mode the login page explains
that browsers must switch to cookie mode. The legacy server-rendered `/login` page is kept as a
fallback/explanation page. Multi-user accounts and role-based permissions are still a design
proposal (`docs/concepts/accounts.md`), not implemented.

```bash
bacmap start web                            # 127.0.0.1:8800 by default
bacmap start web --host 127.0.0.1 --port 8800

# Rebuild the console after frontend changes (development only)
pixi run -e web web-install
pixi run -e web web-build
```

Console routes:

| Route | Purpose |
|---|---|
| `/console/` | dashboard: database overview first, then tasks (KPIs, 7-day trend, status, approvals), then species-first typing stats |
| `/console/tasks` | task list, filters and submit drawer (analyze/curate) |
| `/console/tasks/{id}` | task detail, event timeline, approval card, cancel |
| `/console/plans`, `/console/plans/{id}` | agent-proposed plans, full parameters, confirm/reject |
| `/console/specimens`, `/console/specimens/{id}` | specimens, their isolates and libraries; an inline form links unassigned isolates/datasets to a specimen; the detail page can delete a specimen (empty by default, or unlink its isolates first — isolates/data are kept) |
| `/console/isolates`, `/console/isolates/{id}` | isolate entities, specimen link and libraries |
| `/console/samples`, `/console/samples/{id}` | libraries (sequencing data): per-library results/annotation, a visual assembly-QC panel (QUAST KPIs, contig length/GC distributions, Nx curve) and an embedded “full report” tab |
| `/console/runs`, `/console/runs/{id}` | immutable run records and source comparison |
| `/console/records` | metadata, lab result, knowledge import/approval forms |
| `/console/gom`, `/console/gom/{id}` | GOM objects, immutable versions and payload |
| `/console/research` | research sessions and Study/Cohort/Plan/Claim overview |
| `/console/research/sessions/{id}` | research statistics, figure, artifacts and ledger |
| `/console/research/studies/{id}` | Study, cohorts, plans and claims (read-only) |
| `/console/overview` | system overview (versions, paths, policy, sandbox) |
| `/console/search` | unified search: specimens (background), isolates (wet-lab metadata) and libraries (analysis results) |
| `/research` | advanced research tooling (phylogenetics, logistic, object writes; Jinja) |
| `/samples/{id}/report` | report HTML source (`?embed=1` for the inline frame); direct visits 307 to `/console/samples/{id}?tab=report`, `?download=1` for attachment, `?theme=light|gray` for the light/gray report |
| `/api/v1/*` | JSON API (see [HTTP API reference](../reference/api.md)) |

The sample detail page has “Overview / Full report” tabs; the report renders inside a sandboxed
iframe in the tab instead of opening a separate page. Reports generated by the old template
(without the `bacmap-report` version marker) are re-rendered in the active theme on first access.

The report includes KPI summary cards, AMR class distribution and high-confidence gene bars,
VFDB virulence genes, plasmid replicons, Bakta/eggNOG annotation and COG categories when
available, and collapsible full gene tables.
**AI interpretation**: an external harness/analyst reads the summary, produces
`interpretation_text`, and calls `bio_verify_result` with it; the NLI Reflector checks factual
consistency and persists the text, so the report shows “AI interpretation & NLI self-check”
(passed or needs human review). Without an LLM the report contains deterministic results only.
The dashboard degrades gracefully when `/api/v1/stats` fails: tasks still load and database
statistics show an unavailable message instead of zeroes.

The SPA polls `/api/v1/tasks/{id}` every two seconds while a task is non-terminal. All assets
(CSS, JS, icons, favicon) are local; no CDN or webfont is used (offline-friendly).

### Submitting a task

The form accepts **registered dataset IDs**, separated by ASCII commas or newlines:

```text
SAM-TYP-001, SAM-TYP-002
```

Paths and natural-language requests are rejected. For `curate`, the optional `scope` is a JSON
object:

```json
{"pathogen": "Salmonella", "strains": ["HZCPE-01"]}
```

Use a plan (from an agent) for `mine`/`write`; the form deliberately exposes only `analyze` and
`curate`.

### Approval

When a task reaches `awaiting_approval`, the detail page shows an approval card. The approver name,
decision and signature are recorded in the `approvals` table and emitted as an event. Signing is one
of the human-only actions; agents cannot do it.

## 2. CLI

```bash
bacmap --version
bacmap overview [--json]
bacmap doctor [--json]
bacmap task list|show|submit|approve|cancel
bacmap plan list|show|confirm|reject
bacmap record metadata|lab|knowledge-import|knowledge-approve
bacmap run list|show|compare
bacmap gom list|show
bacmap isolate list|show
bacmap sample ls|show
bacmap search [--query ...] [--serotype ...] [--st ...] [--gene ...]
bacmap results migrate [--dry-run]
bacmap events prune --days N
bacmap backup --out FILE [--with-results]
bacmap restore --from FILE [--force]
bacmap start mcp     # MCP server
bacmap start web     # Web console
bacmap start tui     # task console
bacmap start console  # numbered menu
```

Query commands accept `--json`; task/plan IDs accept unique prefixes, so the 12 characters shown by
`task list` work directly.

### Submit and follow an analysis

```bash
bacmap task submit --type analyze --samples SAM-TYP-001
# => task_id

bacmap task list
bacmap task show 3f9c2a1b
bacmap task show 3f9c2a1b --json | jq .state
```

Register a directory instead of hand-editing samples.tsv:

```bash
bacmap task submit --type analyze --fasta-dir /data/genomes
bacmap task submit --type analyze --fastq-dir /data/run42 --species Salmonella
```

### Curate the local baseline

```bash
bacmap task submit --type curate --scope '{"pathogen":"Salmonella"}'
bacmap task show <task_id>          # ends in awaiting_approval
bacmap task approve <task_id> \
  --approver "Jane Doe" --decision approve --signature "jd-2026-10-30"
```

### Confirm an agent plan

```bash
bacmap plan list
bacmap plan show <plan_id>                 # full tasks, hash, input fingerprints
bacmap plan confirm <plan_id> --version 1 --hash <first 12+ chars>
bacmap plan reject <plan_id> --version 1 --reason "wrong sample"
```

If `--hash` is omitted, `plan confirm` prints the plan and asks interactively; scripts should pass
the hash explicitly.

### Records

```bash
bacmap record metadata --strain-id HZCPE-01 \
  --field isolation_date=2026-10-12 --field province=Guangdong --field sample_source=food
bacmap record lab --strain-id HZCPE-01 --category mic \
  --test-name meropenem --result 0.25 --unit mg/L --interpretation S
bacmap record knowledge-import --title "O3:K6 outbreak" --identifier PMID:12345678
bacmap record knowledge-approve 7
```

Each command submits a `record` task; check it with `bacmap task show`.

### Exit codes and JSON

- `0` success, `1` check failed / operation failed, `2` argument error (argparse).
- `--json` prints one JSON document; diagnostics go to stderr.
- `bacmap doctor` exits `1` only when a check has status `fail`.

## 3. TUI task console

```bash
bacmap start tui
```

The TUI is a dashboard plus explicit operations; there is **no chat**.

| Key | Action |
|---|---|
| `Enter` | run the current slash command |
| `Esc` | cancel a pending approval / focus the input |
| `Ctrl+B` | toggle the sidebar |
| `Ctrl+R` | refresh |
| `Ctrl+L` | clear the log |
| `Ctrl+Y` | confirm a pending signature |
| `Ctrl+G` then `i/l/s/m/t/a/h/q` | focus input / tasks / samples / endpoint / theme / approve / help / quit |

Slash commands:

```text
/help
/clear
/tasks
/samples
/search <keyword>
/model
/result <sample>
/approve <task-id> [signature]
/analyze <sample>
/curate [scope-json]
/quit
```

`/approve` performs a two-step confirmation: the hint bar shows the task and signature; `Ctrl+Y`
submits, `Esc` cancels.

## 4. Interactive console

```bash
bacmap start console
```

A numbered menu for users who prefer prompts over subcommands. It uses the same engine and gates;
it is not a separate implementation.

## 5. JSON API (`/api/v1`)

The Web server also exposes a versioned JSON API under the same authentication. It is a **trusted
operator surface**: whoever holds the Web token can approve and confirm. Never give that token to an
external harness — harnesses use MCP.

```bash
TOKEN=...                         # BACMAP_WEB_TOKEN
curl -s -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8800/api/v1/tasks | jq .

curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"version":1,"plan_hash":"c1d2e3f4a5b6...","confirmer":"jane"}' \
  http://127.0.0.1:8800/api/v1/plans/<plan_id>/confirm
```

Full endpoint and error reference: [HTTP API](../reference/api.md).

## 6. Remote access and authentication

`bacmap start web` binds to `127.0.0.1` by default. For remote access, use an SSH tunnel:

```bash
ssh -L 8800:127.0.0.1:8800 user@workstation
# then open http://127.0.0.1:8800 locally
```

To run the console in the background (survives the terminal), use daemon mode:

### Embedding a local agent chat (DSH / Hermes / opencode)

Instead of keeping bacmap and your agent harness in two windows, embed the
harness's own web UI as a console sidebar page (loopback only, ADR-16 — cloud
frontends cannot be embedded):

```toml
# config.toml
[[web.agent_embed]]
name = "DSH"
url = "http://127.0.0.1:3080/?token=<dsh-browser-trust-token>"

[[web.agent_embed]]
name = "Hermes"
url = "http://127.0.0.1:56791"      # hermes dashboard

[[web.agent_embed]]
name = "opencode"
url = "http://127.0.0.1:49374"      # opencode serve
```

Restart `bacmap start web` — a "智能体对话" sidebar group appears with one
page per entry (`/agent/<n>`). URLs must be http/https loopback addresses
(`127.0.0.1`/`localhost`/`::1`) without embedded credentials — invalid
entries are rejected at config load; a valid entry's
`scheme://host[:port]` origin (no path or query string, so tokens never
leak into response headers) is added to the web CSP `frame-src` allowlist
automatically, while non-loopback entries are skipped. Verified against
DSH (needs its browser-trust token in the URL), the Hermes dashboard and
`opencode serve`. Pi is TUI-only (no web UI to embed).

```bash
bacmap start web -D            # or --daemon
# PID file: $BACMAP_HOME/web.pid · log: $BACMAP_HOME/web.log
bacmap stop                    # graceful stop (SIGTERM, SIGKILL after --timeout)
bacmap restart                 # stop + start again with the last options
```

Starting again while a live daemon is running is refused (stale PID files are ignored).
`bacmap restart` reuses the host/port/token-env recorded at the last daemon start; pass
`--host`/`--port`/`--token-env` to override.

If you bind a non-loopback address, bacmap refuses to start without a token:

```bash
export BACMAP_WEB_TOKEN="$(openssl rand -hex 24)"
bacmap start web --host 0.0.0.0 --port 8800
```

The console only answers requests whose `Host` is a loopback name, the bind address (the
machine's hostname for `0.0.0.0`/`::`) or a name in `BACMAP_WEB_ALLOWED_HOSTS`
(comma-separated); anything else gets `400`. Add the LAN IP or DNS name you browse to, or the
name a reverse proxy forwards:

```bash
export BACMAP_WEB_ALLOWED_HOSTS=192.168.1.20,bacmap.lab.example
```

Two auth modes:

- `bearer` (default): API clients send `Authorization: Bearer <token>`; browsers cannot set this
  header, so the HTML console returns a short 401 explanation (use an SSH tunnel).
- `cookie`: set `BACMAP_WEB_AUTH=cookie`; log in at `/login`; the session cookie is signed and
  `HttpOnly`, and every state-changing POST needs a CSRF token. Add
  `BACMAP_WEB_COOKIE_SECURE=1` behind TLS.

The MCP HTTP transport is separate: it always requires `BACMAP_MCP_TOKEN` (or `--token-env`) and is
covered in [Agents & plans](agent-plans.md).
